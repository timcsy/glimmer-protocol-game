# 開發經驗

## 2026-11-19｜序列關卡擴充為循環教學

### 觀察

- 第一版用按鈕組合前進與轉向，能把「指令順序」直接放進移動路線，符合遊戲先行的方向。
- 原本只有清空整份程式的方式，改錯成本高；加入單條指令刪除後，玩家可以局部修正再執行。
- 音效開關原先只有狀態文字，沒有實際聲音。介面上可操作的控制必須真的完成它宣稱的行為。
- 把重複動作放進第二區的任務目標，比先講解循環語法更貼近「遇到問題才學工具」的設計原則。

### 本次做法

- 以沒有程式先備知識的初學者為預設玩家；第一區只要求排列順序，第二區才引入循環。
- 將循環做成「重複前進 N 次」的可視化指令方塊，讓程式長度與實際移動步數形成可觀察的差異。
- 關卡完成後才解鎖下一區，並保留解鎖進度；每區各自顯示任務、提示與正在學的概念。
- 錯誤訊息保留指令位置，並允許刪除單一指令後重試；成功、移動、收集與碰撞提供音效回饋，且音效預設關閉。

### 可複用範圍

- **新手教學遊戲：** 一次只引入一個新概念，讓它成為通過當前關卡的工具；已學概念留在遊戲中繼續使用。
- **指令編輯器：** 任何能排列步驟的介面，都應提供局部修正方式，避免錯一處就重做全部內容。
- **循環／重複概念：** 可先用具體動作與次數做成區塊，再逐步過渡到一般化的 `repeat` 或迴圈語法。
- **互動一致性：** 開關、按鈕或可操作控制應具有真實效果；若功能尚未實作，就不要呈現成可用控制。
- **無障礙與節奏：** 音效預設關閉，視覺文字仍需完整傳達任務狀態；動畫回饋不可成為完成操作的唯一線索。

### 尚待驗證

- 目前沒有玩家實測；需要觀察初學者能否不看答案完成第一區、理解重複方塊如何縮短程式，以及錯誤後能否自行修正。
- 「重複前進」是為此走廊關卡設計的第一個循環積木；若後續需要重複轉向或組合動作，應擴充成有明確範圍的迴圈容器。

## 2026-11-19｜以環境狀態教條件判斷

### 觀察

- 循環讓同一動作依次重複；條件則要讓玩家先觀察狀態，再決定是否採取動作，兩者需要不同的關卡訊號。
- 只顯示「如果」積木不足以說明分支結果；玩家需要看見條件成立與不成立時角色分別做了什麼。
- 條件教學關卡要把障礙放在可預期的位置，才能讓第一次嘗試的結果可讀，同時仍保留玩家用程式解決問題的必要性。

### 本次做法

- 第三區加入「若前方有障礙，就右轉」指令，讀取機器人前方格子，並根據結果轉向或維持方向。
- 條件成立與不成立都會提供文字回饋與不同提示音；關卡中的巡檢門讓玩家第一次就能看見條件成立的效果。
- 在第三區之前先完成序列與循環關卡，將概念依賴順序固定為：指令順序 → 循環 → 條件。

### 可複用範圍

- **條件判斷教學：** 讓條件讀取遊戲世界中可見的狀態，例如前方障礙、開關或敵人，再讓程式改變角色行為。
- **除錯回饋：** 對分支提供可理解的結果訊息，幫玩家分辨條件真假；之後可逐步減少提示，鼓勵自行推理。
- **關卡設計：** 初次介紹條件時，先用一個清楚的觸發狀態，後續關卡再混入條件不成立、不同狀態或多個分支。
- **概念順序：** 將條件安排在指令順序與重複執行之後，因為玩家已先熟悉指令及狀態變化。

### 尚待驗證

- 玩家仍需實測，確認回饋文字能否幫助他們預測條件結果，而非只依靠提示音或反覆試誤。
- 現有條件方塊只有一個固定分支動作；若加入 `如果／否則`，需要能呈現和編輯兩個分支的介面。

## 2026-11-19｜讓玩家看見條件的兩個分支

### 觀察

- 「如果條件成立才做事」容易把條件的另一種結果藏起來；初學者需要明確看到條件不成立時會發生什麼。
- 只做一個會觸發的測試點，玩家可能記住固定答案，卻不理解同一條件在不同位置會選擇不同分支。
- 在一趟路線上安排條件先成立、後不成立，能讓玩家直接比較兩種結果。

### 本次做法

- 新增可設定成立與不成立動作的 `如果／否則` 方塊，並在程式列中摘要顯示兩個結果。
- 第四區讓同一方塊先遇到牆、再遇到通路，兩個分支都在一次通關中發生。
- 保留簡化的單分支條件作為第三區介紹，再於下一區擴展到雙分支。

### 可複用範圍

- **條件與分支教學：** 初次介紹 `if/else` 時，在同一個可觀察任務中安排兩種狀態，讓玩家看見兩條路徑。
- **可視化程式編輯器：** 可編輯的雙分支應在程式列摘要兩個動作，避免方塊只顯示條件名稱而隱藏行為。
- **由淺入深：** 先用單一條件動作建立直覺，再擴充為成立／不成立兩個分支。

### 尚待驗證

- 尚未有初學者試玩，需確認下拉選單是否比拖拉積木更容易理解，也要確認「不轉彎」這個動作標籤是否清楚。
- 目前的兩分支只允許轉彎或維持方向；未來擴充其他行為時，要避免讓設定面板過於複雜。

## 2026-11-19｜讓已解鎖關卡可以重玩

### 觀察

- 只提供「前往下一區」能推進流程，卻沒有回到舊關卡的方法；玩家因此無法練習已學概念或重新比較解法。
- 關卡解鎖與關卡選擇是兩件事：進度要限制尚未開放的區域，同時讓已開放內容可自由重玩。

### 本次做法

- 在任務標題下加入區域選擇列，顯示關卡序號與概念簡稱。
- 已解鎖的關卡可點選並重置程式，未解鎖關卡呈現鎖定狀態；完成任務後即時刷新解鎖狀態。
- 保留完成關卡後的「下一區」提示，讓首次遊玩可順著故事前進，也讓玩家可自行回頭練習。

### 可複用範圍

- **章節式遊戲：** 以完成進度作為解鎖條件，同時讓已解鎖內容可重玩。
- **學習型產品：** 重玩能力可支援間隔練習、比較不同解法與補強舊概念。
- **進度介面：** 同時呈現目前所在區域、已解鎖範圍與下一步，避免玩家誤以為只能單向前進。

### 尚待驗證

- 初學者試玩仍是必要工作；需確認區域簡稱是否能讓人預測關卡內容，以及鎖定狀態是否足夠清楚。

## 2026-11-19｜以局部移動修正指令順序

### 觀察

- 只提供刪除與清空，仍會讓玩家為了修正一個位置而重建後續指令。
- 讓玩家移動單一方塊，可直接呈現「同一組指令，順序不同，結果也不同」的概念。

### 本次做法

- 每個指令方塊加入上移與下移控制，並在序列邊界停用不可能的方向。
- 重新排序後保留所有指令，只更新序列與步數，再讓玩家重新執行驗證。
- 保留刪除控制，讓玩家可選擇調整順序或移除多餘指令。

### 可複用範圍

- **指令／工作流程編輯器：** 編輯有序步驟時，提供移動與刪除等局部操作，降低反覆重建成本。
- **程式概念呈現：** 可用同一組步驟的不同排列，讓玩家探索順序對結果的影響。
- **鍵盤與輔助操作：** 每個移動按鈕應標明目標指令序號，序列邊界應使用真正停用狀態避免無效操作。

### 尚待驗證

- 仍需觀察新手能否分辨上移／下移按鈕作用在哪個指令，以及在手機窄螢幕上的操作是否順手。

## 2026-11-19｜把核心玩法檢查固化為自動測試

### 觀察

- 一次性冒煙檢查能快速驗證原型，但後續關卡修改容易不小心破壞已完成路線或進度行為。
- 自動測試可以驗證遊戲狀態與互動邏輯，卻無法判斷新手是否理解畫面、任務或學習概念。

### 本次做法

- 使用 Node.js 內建測試執行器與簡單 DOM 假物件，無需安裝額外套件。
- 固定檢查序列、循環、條件與雙分支通關，並覆蓋碰撞回饋、解鎖／重玩、進度保存和指令編輯。
- 將執行命令寫入 README，讓後續每次修改都可快速重跑。

### 可複用範圍

- **小型靜態遊戲：** 若核心玩法由純 JavaScript 狀態與少量 DOM 更新構成，可先用 `node:test` 加假 DOM 做快速回歸檢查。
- **迭代節奏：** 對已確認的重要路線和進度行為保留自動檢查，縮短每次修改後的驗證時間。
- **驗證界線：** 自動測試只驗證程式行為，不取代真實玩家試玩或視覺版面檢查。

### 尚待驗證

- 目前測試以假 DOM 驗證互動邏輯；需要真實瀏覽器檢查窄螢幕排版、音效體驗和鍵盤操作。
- 玩家是否理解循環、條件和任務內容仍需初學者試玩確認。
